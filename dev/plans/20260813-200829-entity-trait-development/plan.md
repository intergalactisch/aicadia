## Alignment

### Strategic

Traits make a shared Entity recognizable across time. Pip can begin as a rat that
“startles at every hard sound” and later become one that “waits for the second echo
before springing” without gaining a level, score or executable ability. A later User
and Agent can encounter the current characterization and its accountable history,
turning prior play into a grounded callback and a new decision.

This deliberately evolves the current contract rather than merely polishing
Properties. It retains one World authority, one Entity identity, Entity-owned state,
explicit confirmation and immutable Activity. The resolved projection keeps local
orientation and historical/mutation references compact, then returns one selected
Entity with one bounded typed current-state page. That avoids N+1 reads, recursive
Activity hydration and oversized list results without reviving a separate Property
inventory. The plan is accepted, deterministic delivery and T7 review are complete,
and T8 has frozen, preflighted and independently approved the live candidate without
starting a model.

### Tactical

Rounds 1–3 fix these boundaries:

1. Entity creation accepts no Trait input. A Trait is established contextually only
   when an accepted Action or Interaction makes the characterization relevant.
2. Existing `submit_action` and `submit_interaction` both gain explicit Trait
   establishment/development consequences backed by one private World writer. An
   Interaction Trait consequence never authors a target response, thought, consent
   or volition.
3. Action eligibility is exactly actor, current Place, other Characters at that
   Place and explicitly placed ordinary Entities, with no role/control branch.
4. Establishment creates one World-assigned stable Trait id and first immutable
   version. Development names that id, appends a predecessor-linked statement and
   advances one current pointer. Retirement remains absent.
5. Trait statement text remains non-executable. World checks only shape, identity,
   eligibility, freshness and transaction rules.
6. Every Entity owns its Property and Trait state. `get_character` returns its
   Character Entity with correct current associations; any other Entity fetch does
   the same. The Agent decides use/relevance. No observer-specific knowledge model
   exists. Property/Trait are state, not Relationship.
7. Interaction Trait eligibility is actor plus every explicit target, uniformly
   across Entity roles. A User especially does not directly control Trait storage.
8. Action uses one closed `trait_change[1..100]` containing typed `establish` and
   `develop` items. Interaction uses optional `trait_change[0..100]`, may mix both
   lifecycle items and may coexist atomically with Property changes.
9. World rejects unchanged development and any exact normalized duplicate in the
   intended post-package active statement set per Entity, accepts semantic
   contradictions, lets one lineage supersede only itself and infers no precedence
   over another Trait, Property or description.
10. Only explicit confirmed Action and Interaction are executable causes. A future
    external deterministic writer remains absent.
11. `list_entity_at_current_place` stays compact. `get_character` and new scoped
    `get_entity_at_current_place` return the selected Entity plus one combined typed
    current Property/Trait association page. The latter accepts exactly one eligible
    local Entity id. Existing `list_entity_property_at_current_place` is removed;
    replacing it keeps the player catalog at exactly thirteen.
12. The Agent authors the exact Trait consequence, presents natural prose plus every
    affected Entity/lifecycle item and current/new characterization where applicable,
    preserving stable lineage continuity without showing a UUID, and waits for
    whole-package User acceptance or rejection. The User
    receives no direct Trait editor and no post-confirmation Trait may be hidden.
13. Every immutable Trait statement version is PostgreSQL `text`, trimmed, non-NUL
    and 1–4,000 Unicode characters. Richer causal narrative belongs in Activity
    prose rather than turning current state into a chronicle.
14. One mixed package rejects duplicate establishment `(entity_id, normalized
    statement)`, duplicate development of one `trait_id`, development to its exact
    current statement and duplicate exact statements in the intended final active
    set for one Entity. That final-set rule covers develop-to-other-active,
    two-develop-to-same and establish-plus-develop-to-same; a statement vacated by
    another development in the same unordered package may be reused. Semantic
    near-duplicates and contradictions remain accepted.

### Technical design commitments

- Trait ids are World-generated UUIDs and stable lineage selectors exposed as part
  of an actually fetched Entity's current state.
- Statement normalization trims outer Unicode whitespace, rejects U+0000, then
  validates 1–4,000 Unicode characters. It preserves internal whitespace, case,
  punctuation and code points; “exact” duplicate/no-op comparison uses only that
  stored trimmed statement and performs no Unicode folding or semantic inference.
- The combined current-state page uses one tagged association union and one cursor,
  default limit 25 and accepted limits 1–100. Property associations sort before
  Trait associations; Properties sort by immutable internal Property-key id (never
  exposed) and Traits by stable Trait id. This is a read projection, not a shared
  persistence/mutation abstraction.
- Trait-change lists are semantic unordered sets. Fingerprints sort typed establish
  items by `(entity_id, statement)` and develop items by `(trait_id, statement)`.
- Exact active-statement uniqueness is evaluated on the simultaneous intended final
  set per Entity, never by request order. Develop-to-other-unchanged-active,
  two-develop-to-same and establish-plus-develop-to-same reject the complete Action
  or Interaction; reuse of a statement vacated within that package succeeds.
- Current-state cursors are operation-specific and bind selected Entity, nullable
  current Place identity/revision and last typed sort key. A later page returns the
  same Place revision; any intervening placement/Property/Trait change yields the
  existing neutral stale-revision result rather than mixing snapshots. An unplaced
  Character has null Place/revision and cannot receive contextual Trait changes.
- Canonical errors are `invalid_trait` for statement/lifecycle/count/duplicate/no-op
  violations, `invalid_entity_limit` for a state-page limit outside 1–100,
  `invalid_request` for malformed/cross-operation cursors,
  `entity_at_current_place_unavailable` for a well-formed absent/remote/departed
  selected Entity, neutral `trait_unavailable` for a well-formed missing/stale/
  ineligible Trait mutation and existing `place_revision_conflict` when a continuation
  snapshot changed. None splits existence, role or control cases.
- `entity_trait_version.activity_id` is indexed but not unique because one Activity
  may change multiple Traits. Activity hydration uses one batched query for all page
  ids after the existing Activity lens authorizes them.
- The dedicated runner uses `dev/playtest/trait/run`,
  `dev/playtest/trait/schema/`, `dev/tests/trait-playtest.sh` and its own private
  `dev/.playtest/trait/` evidence root frozen by T8.

## Accepted database contract

The delivered three-table schema is:

```text
entity_trait
  id uuid primary key
  entity_id uuid not null references entity(id) on delete restrict
  unique (id, entity_id)
  index (entity_id, id)

entity_trait_version
  trait_id uuid not null
  entity_id uuid not null
  activity_id uuid not null references activity(id) on delete restrict
  previous_activity_id uuid null
  statement text not null + trimmed/non-NUL/1..4000 Unicode-character check
  primary key (trait_id, activity_id)
  unique (trait_id, entity_id, activity_id)
  foreign key (trait_id, entity_id)
    references entity_trait(id, entity_id) on delete restrict
  foreign key (trait_id, entity_id, previous_activity_id)
    references entity_trait_version(trait_id, entity_id, activity_id)
  unique (trait_id, previous_activity_id) where previous_activity_id is not null
  unique (trait_id) where previous_activity_id is null
  index (activity_id, entity_id, trait_id)

entity_trait_current
  trait_id uuid primary key
  entity_id uuid not null
  current_activity_id uuid not null
  foreign key (trait_id, entity_id)
    references entity_trait(id, entity_id) on delete restrict
  foreign key (trait_id, entity_id, current_activity_id)
    references entity_trait_version(trait_id, entity_id, activity_id)
  index (entity_id, trait_id)
```

`entity_trait` is only the immutable stable identity/owner row; it is not an Entity
or mutable profile. `entity_trait_version` is the sole statement and provenance
store and is append-only. Its unique null-predecessor root is the establishment, so
that root's `activity_id` is the one authoritative establishing Action/Interaction;
no duplicate root Activity pointer can drift. Development stores the prior current
version's Activity as predecessor. The partial uniqueness rules prevent two roots or
branches even outside normal World code. `entity_trait_current` stores only a pointer
and is updated under stable locks. Retirement is absent, so every root has one
current row. Deferred per-Trait constraint triggers validate the affected id at
transaction commit, after the writer's legal insert/update order: every stable Trait
has exactly one root, exactly one current pointer and no successor after that current
version. An incomplete identity/root, current deletion, pointer backtracking or a new
successor without its matching pointer advance cannot commit. Primary, partial
unique and predecessor indexes keep each affected-Trait check bounded rather than a
global Trait scan.

The migration must extend the existing closed Action discriminator with one mixed
closed Trait-change consequence and admit the same typed items under
`submit_interaction`. Trait values never enter Entity creation, `entity_property`,
JSONB, Activity prose or a universal event payload. Property and Trait remain two
Entity-owned state models, never a Relationship or observer-knowledge model.

The shared Action/Interaction writer resolves and locks all affected Entity rows by
UUID order, then all existing current Trait rows by Trait id order. Establishment
locks each Entity before exact-active-statement validation; development verifies
that every Trait is current and eligible for that cause under the request's current
Place revision, then uses the locked `entity_trait_current.current_activity_id` as
the new version's predecessor. The public item deliberately needs no expected-
predecessor field: request Place revision plus current-row lock is the freshness
guard. It bulk-inserts roots/versions,
bulk-upserts current pointers, inserts Activity/participation and commits once. Any
duplicate, stale selection, storage race or unavailable subject rolls back every row.
Before writing, it derives every affected Entity's intended final active statement
set. It rejects develop-to-other-unchanged-active, two-develop-to-same and
establish-plus-develop-to-same collisions, but permits reuse of a statement whose
owning lineage is developed away in the same unordered package. Either Action or
Interaction rejects atomically, including Interaction Property changes.

## Accepted public interface contract

### Creation

`CreateEntity`, `CreateCharacter`, `CreateEntryPlace` and
`submit_action.introduce_entity` remain unchanged and reject any `trait` field as
unknown input. A Character, Place or ordinary Entity begins without Traits. The first
Trait can arise only through a later contextual accepted Action or Interaction.

### Action

Action carries contextual Trait establishment/development over its confirmed uniform
exact-local Entity set through one closed consequence:

```text
change_entity_trait {
  trait_change: [
    {type: "establish", entity_id, statement} |
    {type: "develop", trait_id, statement}
  ] // 1..100 total
}
```

Establishment names an exact local Entity. Development derives the owner from its
stable Trait id and requires a current Trait on an eligible exact-local Entity. One
list may establish and develop different Traits atomically. The exact duplicate/no-op
scope rejects duplicate establish `(entity_id, normalized statement)`, duplicate
develop `trait_id`, an exact-current development and any duplicate exact statement
in the intended post-package active set for one Entity. Development into another
unchanged active statement, two developments to one final statement and an
establishment plus development to one final statement reject; a statement vacated
by another development in the same package may be reused.

A `develop` item contains no predecessor/version selector. The request's existing
expected Place revision prevents development from a stale observed situation; under
that revision World locks the Trait's current pointer and records that exact current
version as predecessor. Fingerprints therefore contain lifecycle, `trait_id` and new
statement, while accepted output/history supplies previous/current statements and
version provenance. Equal retry still reconstructs the original result before live
freshness checks.

Before either mutation, the Agent naturally previews the complete outward prose and
every Trait item. Establishment preview names lifecycle, affected Entity and new
statement; development names the same stable characterization naturally plus exact
current and new statements, without showing its UUID. The User accepts or rejects
the whole package. Steering may ask the Agent
to revise its proposal, but no direct Trait editor or hidden post-confirmation
consequence exists.

`AcceptedAction.consequence` returns the exact sorted established/developed Traits,
including generated stable ids and previous/current statement where applicable.
Equal delivery retry reconstructs the original accepted result from Activity/version
rows before current preconditions. Changed input with the same request id remains
`action_request_conflict`.

### Interaction

`submit_interaction` gains optional `trait_change[0..100]` with the same typed mixed
establish/develop items and private writer. Eligible Trait subjects are exactly the
actor and explicit targets, uniformly across Entity roles. Empty retains current
outward behavior. One accepted Interaction commits outward prose, participation,
any Property changes, Trait roots/versions/current pointers and Place revision
atomically. A target Trait change is a World consequence of the encounter, never a
target-authored response, thought, consent or volition. Equal retry returns the
original generated Trait ids and versions; changed Trait content conflicts under
the existing Interaction request identity.

### Entity reads and Activity

Current Property and Trait collections are associations on the fetched Entity, not
separate observer facts. The Agent, not World, decides which fetched facts matter to
the situation. World stores no per-observer Knowledge, Observation or receipt state.
The exact player projection is:

```text
GetEntityCurrentStateInput {
  cursor?: string,
  limit?: integer // default 25, accepted 1..100
}

GetEntityAtCurrentPlaceInput {
  entity_id,
  cursor?: string,
  limit?: integer // default 25, accepted 1..100
}

EntityCurrentAssociation =
  { type: "property", property: { key, value } } |
  { type: "trait", trait: { id, statement } }

ActivityTraitChange =
  { type: "establish", entity: EntitySummary, trait: { id, statement } } |
  { type: "develop", entity: EntitySummary,
    trait: { id, statement }, previous_statement }

EntityCurrentStatePage {
  association: [EntityCurrentAssociation],
  next: string | null
}

CharacterEntityStatePage {
  character: Character,
  place_revision: string | null,
  current_state: EntityCurrentStatePage
}

CurrentPlaceEntityStatePage {
  place: CurrentPlaceOutput,
  place_revision: string,
  entity: CurrentPlaceEntityOutput,
  current_state: EntityCurrentStatePage
}

get_character(user_id, GetEntityCurrentStateInput)
  -> CharacterEntityStatePage

get_entity_at_current_place(user_id, GetEntityAtCurrentPlaceInput)
  -> CurrentPlaceEntityStatePage
```

HTTP uses `GET /api/character?cursor&limit` and
`GET /api/place/current/entity/{entity_id}?cursor&limit`; MCP uses the operation names
above. Omitted cursor means the first page. Unknown fields, malformed operation-
specific cursors and limits outside 1–100 reject strictly and identically through
World, HTTP and MCP.

One combined typed page is the smallest complete interface: it keeps Property and
Trait meanings explicit while giving callers one cursor and one bounded payload.
Associations sort first by type (`property`, then `trait`), then Properties by
immutable internal Property-key id (not exposed) and Traits by stable id. Association
values omit the repeated parent Entity because each page belongs to exactly one
returned Entity. Cursors are opaque,
operation-specific and bind the selected Entity, nullable current Place identity and
revision, and last typed sort key. Every continuation repeats the same Entity and
Place revision; a changed revision returns `place_revision_conflict`, while a
no-longer-local Entity returns neutral `entity_at_current_place_unavailable`, rather
than mixing snapshots. An unplaced Character
returns null `place_revision`; its creation-time Properties are stable and it cannot
receive a contextual Trait before entry.

`list_entity_at_current_place` remains compact orientation. The new exact-local read
accepts actor, current Place, co-present Character or explicitly placed ordinary
Entity under one role/control-neutral eligibility rule. It replaces and removes
`list_entity_property_at_current_place`; one tool out and one tool in leaves exactly
thirteen player capabilities: `get_world`, `get_user`, `get_character`,
`create_character`, `create_entry_place`, `enter_world`, `list_activity`,
`create_entity`, `list_entity_at_current_place`,
`list_activity_at_current_place`, `get_entity_at_current_place`, `submit_action` and
`submit_interaction`. `get_character` and
`get_entity_at_current_place` are the only full player Entity fetches. Entity/Place
values nested in creation, entry, Action or Interaction results and every Activity
Entity reference are compact acknowledgements/references, not fetches, and never
recursively carry current associations; their existing safe identity/role fields are
otherwise preserved.

Activity gains sorted `trait_change`, hydrated in one batched query after existing
personal/Place authorization. It records exact historical Property/Trait consequences
without recursively attaching current state. Mutation remains inside existing
`submit_action` and `submit_interaction`; no new mutation tool is added.
