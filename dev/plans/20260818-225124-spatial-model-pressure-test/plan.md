# Pressure-test four temporary spatial models

> **Role / side:** execution plan for one decision-oriented spatial lab / development side.
> **Authority:** owns the bounded task, state and evidence for comparing four temporary spatial model shapes against the accepted scenario catalogue.
> **Excludes:** accepted vocabulary, product behavior, schema and runtime implementation; those remain in `dev/CONTEXT.md`, `game/docs/` and runtime surfaces.

## Outcome

The User receives one evidence-bounded recommendation about which temporary model
best explains all thirteen spatial hard cases without turning authored meaning,
exact Position, movement, topology, privacy and remote causality into synonyms. The
lab must expose every candidate's smallest state, reads, writes, invalidation,
visibility and hot-subject cost. Its verdict informs the next grill but accepts
nothing automatically.

- Choosing or adding canonical terminology, fields, tables, endpoints or capabilities.
- Implementing or benchmarking World, PostgreSQL, HTTP, MCP, Agent or spatial indexes.
- Claiming production correctness, latency, throughput or million-User capacity.
- Solving each scenario with one universal primitive.

## Alignment

### Strategic

Aicadia's exploration and settlement loop depends on Agents describing unusual
spatial situations without corrupting multiplayer truth. This test prevents a
convenient coordinate or universal-relation model from becoming long-lived debt
before terrain, carrying, moving Places, privacy and remote Actions are considered.

### Tactical

Compare exactly four temporary shapes: exact point only; exact point plus free
description in one Position; direct-or-relative Position plus separate authored
meaning; and multiple generalized spatial facts. For SP01–SP13, classify support,
qualification or failure and state the concrete reason. Then compare the candidates
across Agent input, stored truth, reads, movement, visibility, transactions and
massive-concurrency pressure and select one leading direction with explicit gaps.

### Technical

The experiment is a token-free paper model. No implementation seam is real. It may
reason from existing primary-source research and PostgreSQL/game constraints, but
cannot claim measured performance. Any surviving technical uncertainty becomes a
later separately planned Rust/PostgreSQL experiment only if it could change the
product choice.

## Task details

### T1 — Compare the four candidates

**Objective:** A reader can reproduce why each candidate passes, qualifies or fails
each fixed scenario and why the leading candidate deserves the next grill.

**Actions:**

1. Define the candidates without canonical names and fix pass/qualified/fail criteria.
2. Evaluate all thirteen scenarios and every cross-scenario pressure dimension.
3. Record a bounded verdict, falsifiers, non-claims and exact remaining choices.
4. Link the lab track and record only its implication in the active concept trail.

**Invariants:**

- No candidate alters the scenario fixture to improve its result.
- A free phrase never grants mechanics, visibility, access or causal authority.
- One hot carrier cannot be declared scalable when the model requires descendant rewrites.
- Hidden state is filtered before Agent context and guessed identities reveal nothing.
- No lab-local term enters `dev/CONTEXT.md`, Areas, `game/docs`, schema, API or code.

**Evidence:**

- Focused `rg` audit — all four candidates, SP01–SP13, eight dimensions, verdict, falsifiers and non-claims exist.
- `cargo test -p aicadia-studio --test studio the_documentation_lint_is_clean` — governed links and metadata remain valid.
- `git diff --check` — no whitespace errors.

**Stop conditions:**
